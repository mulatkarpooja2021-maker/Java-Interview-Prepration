SPRING JPA

1. REQUIRED (default)

Joins the existing transaction if available; else creates a new one.

Use Case: General service methods.

2. REQUIRES_NEW

Always creates a new transaction, suspending any existing one.

Use Case: Logging, auditing, or any operation that must commit independently.

3. SUPPORTS

Uses the current transaction if available; else runs without one.

Use Case: Read operations where a transaction is optional.

4. NOT_SUPPORTED

Always runs without a transaction. Suspends any existing one.

Use Case: Read-only operations or external service calls.

5. NEVER

Throws an exception if there is an active transaction.

Use Case: Enforce that no transaction should exist.

6. MANDATORY

Must run inside an existing transaction; throws an exception if none.

Use Case: Helper methods that require a transaction context.

7. NESTED

Starts a nested transaction within the existing one using savepoints.

Use Case: When you want to roll back part of a transaction without affecting the whole.

volatile in Java
What it does

volatile guarantees visibility, not atomicity.

If Thread A updates a volatile variable

Thread B will immediately see the updated value

It prevents threads from reading stale values from CPU cache.

What it does NOT do

❌ Does not make compound operations thread-safe
❌ Does not prevent race conditions

Example
volatile boolean flag = false;

Thread A: flag = true;
Thread B: if (flag) { ... }  // guaranteed to see true

But this is NOT safe:
volatile int count = 0;

count++; // NOT atomic


Why?
Because count++ = read → increment → write (3 steps)

    return repo.findById(id).map(u -> new Found(UserDto.from(u)))

    throw new IllegalStateException("Unhandled: " + r.getClass());

I first identify whether workload is CPU-bound or IO-bound.
For CPU-bound tasks I keep pool size near CPU cores.
For IO-bound tasks I calculate using wait/compute ratio and align pool size with downstream resources like DB connection pools to avoid thread starvation.
Then I validate using monitoring and load testing.

Kafka Architecture

KAFKA FAILURE SCENARIOS

Kafka is designed to handle failures in distributed systems without losing data. Below are common Kafka failure scenarios.

Broker Failure

Scenario: A Kafka broker (server) crashes.

Example cluster:
Broker1
Broker2
Broker3

Example partition replication:
Partition-0 → Leader (Broker1), Replica (Broker2)
Partition-1 → Leader (Broker2), Replica (Broker3)

If Broker1 crashes:
Partition-0 leader automatically switches to Broker2.

Kafka uses replication and leader election to recover automatically. If replication is configured properly, there is no data loss.

Producer Failure

Scenario: Producer crashes while sending messages.

Flow:
Producer → Kafka Topic

If producer fails:
The message might not reach Kafka.

Solution:
Enable retries and acknowledgments.

Example configuration:
spring:
  kafka:
    producer:
      acks: all
      retries: 3
      properties:
        enable.idempotence: true
        delivery.timeout.ms: 120000
        request.timeout.ms: 30000 # wait for the broker response time

120000 ms = 120 seconds = 2 minutes

delivery timeout = total time for retries

Producer sends message
Broker not responding
Producer retries
Producer retries again
Producer retries again


retries=3
acks=all

Explanation:
acks=all → Producer waits until all replicas confirm the message.
retries=3 → Producer retries sending the message if it fails.


If message is still not delivered after 2 minutes, Kafka throws an error.




Consumer Failure

Scenario: Consumer crashes while processing messages.

Example:
Topic partitions assigned to Consumer1 and Consumer2.

If Consumer1 crashes:
Kafka triggers a consumer rebalance.

Result:
Consumer2 takes the partitions of Consumer1 and continues processing.

Message Processing Failure

Scenario: Consumer reads the message but business logic fails.

Example:
Consumer reads message but database insert fails.

Solutions:
Retry mechanism
Dead Letter Topic (DLT)

Flow:
order-topic → consumer fails → retry → retry → retry → if still failing → send to order-topic-dlt

Dead Letter Topic stores failed messages for later analysis or reprocessing.

Network Failure

Scenario: Network disconnect between consumer and Kafka broker.

Example:
Consumer cannot communicate with broker.

Kafka behavior:
Consumer heartbeat stops.
Kafka detects failure and removes the consumer.
Kafka triggers consumer rebalance.

Other consumers take over the partitions.

Disk Failure

Scenario: Kafka broker disk fails.

Kafka uses replication.

Example:
Partition-0
Leader → Broker1
Replica → Broker2
Replica → Broker3

If Broker1 disk fails:
Broker2 becomes the new leader.

Messages remain available through replicas.

Offset Commit Failure

Scenario: Consumer processes message but offset is not committed.

Example:
Consumer processes message and crashes before committing offset.

Result:
When consumer restarts, it reads the same message again.

This causes duplicate processing.

Solution:
Use idempotent processing or exactly-once processing.

Kafka Cluster Failure

Scenario: All brokers go down.

Example:
Broker1 down
Broker2 down
Broker3 down

Result:
Producers cannot send messages.
Consumers cannot read messages.

Solution:
Use monitoring, multi-region clusters, and backup strategies.

Real Production Failure Example

Payment processing system:

Payment Service → Kafka Topic → Payment Processor → Database

Failure scenario:
Database goes down.

Handling approach:
Retry processing.
If retries fail, send message to Dead Letter Topic.
Later reprocess failed messages.

Best Practices for Kafka Failure Handling

Use replication factor of at least 3.
Enable producer retries.
Use dead letter topics for failed messages.
Monitor consumer lag.
Implement idempotent consumers.
Use retry topics for temporary failures.

Interview Question

What happens if a Kafka consumer fails?

Answer:
Kafka detects missing heartbeat from the consumer and triggers consumer rebalance. The partitions assigned to the failed consumer are reassigned to other consumers in the same consumer group so processing can continue.

👉 This defines WHEN to open the circuit

resilience4j:
  circuitbreaker:
    instances:
      paymentService:
        registerHealthIndicator: true
        slidingWindowSize: 10
        minimumNumberOfCalls: 5
        failureRateThreshold: 50
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 3
🔥 Meaning (VERY IMPORTANT)
Property	Meaning
slidingWindowSize: 10	            Last 10 requests are tracked by intervepter
minimumNumberOfCalls: 5	              Start evaluation only after 5 calls
failureRateThreshold: 50		      If 50% fail → OPEN circuit
waitDurationInOpenState	               Stay OPEN for 10 sec
permittedNumberOfCallsInHalfOpenState:3	Trial requests
🔥 Example Scenario

Out of 10 calls:

6 failed ❌

Failure rate = 60%

👉 Threshold = 50%
👉 Circuit → OPEN 🚫
👉 All calls → Fallback

🔹 3. Rate Limiter Configuration

👉 Controls how many requests allowed per time

✅ Example
resilience4j:

    instances:
      paymentService:
        limitForPeriod: 5
        limitRefreshPeriod: 1s
        timeoutDuration: 2s
🔥 Meaning
Property	Meaning
limitForPeriod: 5	Max 5 requests
limitRefreshPeriod: 1s	Per second
timeoutDuration: 2s	Wait time if limit exceeded
🔥 Example

👉 10 requests hit at same time:

Next 5 → wait / fail ❌ (based on timeout)

)

    @Bean
    @ConfigurationProperties(prefix = "spring.datasource.db1")
    public DataSource db1DataSource() {
        return DataSourceBuilder.create().build();
    }

    @Bean
    public LocalContainerEntityManagerFactoryBean db1EntityManager(
            EntityManagerFactoryBuilder builder) {

        return builder
                .dataSource(db1DataSource())
                .packages("com.example.entity.db1")
                .persistenceUnit("db1")
                .build();
    }

    @Bean
    public PlatformTransactionManager db1TransactionManager(
            EntityManagerFactory db1EntityManager) {

        return new JpaTransactionManager(db1EntityManager);
    }
}

Spring MVC follows a blocking, thread-per-request model which is simple but not scalable under high I/O latency.

⚠️ Important reality

Thread pool
Context switching

Reactive programming
============================================================================
Uses event loop (like Netty)
Very few threads handle thousands of requests
Uses non-blocking I/O
🧠 Analogy expansion
Waiter takes order → gives you a token/buzzer
Waiter moves on immediately
Kitchen prepares food
When ready → you (or system) get notified
No waiting, no blocking
